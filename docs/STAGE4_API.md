## Store and lifecycle

`SCHEMA_VERSION=4`, `MIGRATABLE_SCHEMA_VERSIONS=(1,2,3)`. Existing store helper signatures, identity, database filename and exclusive data lock are unchanged. `schema_v4.sql` appends `schedule_status` and `schedule_operations`; new/explicitly migrated stores start disabled, six-hour interval, config version 1, cursor 0, null due/attempt/success/run and no replay records. `require_schema(version=4)` requires both tables and the singleton; legacy validation remains scoped to its version. Existing v1/v2/v3 service startup refuses implicit migration. The existing stopped-service migration applies v4 in its transaction. No migration has been run.

`schedule_status` persists enabled, interval, configuration version, next wall due, last completed attempt/success timestamps, last outcome/error, feed version, committed cycle index/identity and saved run ID. During an active attempt `in_progress` is an in-memory guard indication; the new attempt becomes durable with its outcome. `schedule_operations` contains committed cycles only, keyed by operation UUID and unique `(actor_id,idempotency_key)`, with canonical payload hash and immutable result JSON including the nine batch IDs.

One `SyntheticScheduler` thread is started after database readiness in the existing API process. It uses the same `run_lock` as ordinary `POST /api/runs`. API shutdown signals and joins it before releasing the existing exclusive app-data lock. The current in-flight operation finishes or rolls back before shutdown completes. No OS cron, service, queue, extra worker, dependency or missed-run backlog is introduced.

The timer reads its saved due time, makes at most one overdue attempt on restart, then schedules from completion/failure time plus the configured interval. It never advances once per missed interval. Failed/busy automatic attempts schedule forward; failure-record loss also installs a process-local forward deadline and visible `timer_error` so the overdue cursor cannot trigger a rapid acquisition loop. That retry guard is bound to its captured `(config_version,next_due_at)` and is ignored after either changes, including when an old attempt finishes recording failure after a new configuration save. Manual acquisition may run while disabled. A committed manual acquisition reschedules the enabled timer forward. Saving any configuration sets a new deadline from that save, without advancing scenario time. Disabled state has no due timestamp. The interval is bounded to integer 1–168 wall-clock hours, default 6.

The scenario clock is independently fixed to `2026-09-01T00:00:00.000Z + cycle_index * 6 hours`. First advancement is cycle 1. At cycle 1460 further acquisition fails visibly with `FEED_EXHAUSTED`; no wrap/reset occurs. An existing committed key can still replay at exhaustion or with unavailable assets. An enabled exhausted schedule can be explicitly disabled; attempted further automatic cycles remain visible failures at the configured future deadline.

Whole-store backup/restore retains clock, cursor, enabled/due/configuration, operations, evidence, runs and audits together. Restoring an older snapshot loses keys/results newer than that snapshot; no exactly-once guarantee exists outside retained history. Restore itself starts no timer. Assets and producer code are external to the database and must still be compatible when serving the restored store. Core owns state command behavior/help/docs; Stage 4 does not rewrite those algorithms.

## Atomic cycle and evidence

The shared nonblocking run guard spans preparation and completion; concurrent timer/manual/ordinary-run attempts return busy. After a read-only capture of cursor/configuration/replay, the connection is closed and the complete deterministic bundle is prepared outside SQLite. Inside `BEGIN IMMEDIATE`, replay, cursor/configuration/due state and current rich inventory/source authority are rechecked. A stale prepared bundle cannot become the next cycle.

One transaction then updates only `app_meta.demo_clock_at`, calls the existing importer directly for all nine envelopes, creates the existing reconciliation run, synchronizes exceptions, saves committed operation/cursor/status and appends the successful acquisition audit. It commits once. It does not modify seed provenance, prior batches/runs, intended baseline versions, allocation tokens or current DHCP approval checks. Ordinary import clock equality validation and separately committed manual imports are unchanged. RFP-043's general import callback remains deferred.

Unexpected rejected/duplicate rows, replayed import receipts, malformed bundles or unexpected incomplete receipts fail the whole cycle. The reviewed producer's explicitly incomplete North routing coverage (phase 5) can commit as `partial`; absence remains unknown in saved results. Stale Central views (phase 7) retain declared completeness but produce unknown calculations as appropriate: acquisition `complete` describes accepted envelopes, not healthy or complete findings. Failure rolls back clock, imports, run, exception changes, cursor and committed replay record. A separate transaction records failure audit/status without replacing the previous successful cycle/run. If that recording also fails, the HTTP error reports `audit_recorded=false` and `failure_recorded=false`, adds a visible message and logs the loss; timer status exposes it. A busy timer does not overwrite an active acquisition's pending status; that operation owns its final deadline/outcome.

## HTTP contract

These are fixed demo identities, not authentication. Existing `GET /api/actors` supplies permissions. Configuration and Run now require `inventory_edit`, currently `demo-approver`. Timer actions use the internal system actor. Callers cannot request a trusted system action.

| Route | Request | Response |
|---|---|---|
| `GET /api/schedule` | None | Persisted fields plus actual `demo_clock_at`, `in_progress`, `eligibility: {eligible,error}`, and process-local `timer_error` |
| `POST /api/schedule` | `actor_id`, nonempty `reason` (max 500), `expected_config_version`, boolean `enabled`, integer `interval_hours` (1–168) | Current status after commit; stale version is 409 `STALE_SCHEDULE`; enabling requires eligibility; disabling is allowed when assets/authority are unavailable |
| `POST /api/schedule/run` | `actor_id`, nonempty `reason` (max 500), nonempty `idempotency_key` (max 200) | 201 new committed result; 200 exact replay, with `X-Acquisition-Replay`; failed/busy requests never claim a new saved run |

Status fields: `enabled`, `interval_hours`, `config_version`, `next_due_at`, `last_attempt_at`, `last_success_at`, `last_outcome` (`complete|partial|failed|busy|null`), `last_error`, `feed_version`, `cycle_index`, `cycle_id`, `demo_clock_at`, `run_id`, `in_progress`, `eligibility`, `timer_error`. All wall timestamps are UTC with millisecond precision. `last_success_at` includes a valid partial commit. Failure leaves the last committed cycle/run fields intact.

Committed result: `operation_id`, `feed_version`, `cycle_index`, `cycle_id`, `demo_clock_at`, `run_id`, `outcome` (`complete|partial`), `completed_at`, `batch_ids`, `replay`. Matching actor/key/canonical payload returns that stored result without another run/audit/clock change; changing the payload for a committed key is 409 `IDEMPOTENCY_CONFLICT`. Failed attempts have no committed key record and may retry the same payload. Busy is 409 `RUN_IN_PROGRESS`; SQLite contention keeps existing `STORE_BUSY` behavior. Preparation, authority, import and exhaustion errors remain explicit and do not advance the cursor. Original result details/export continue at `/api/runs/{run_id}` and `/api/runs/{run_id}/export`.

The Schedule panel displays the two clocks and saved run identity separately. Before POST it saves the exact manual payload/key in per-tab `sessionStorage` and reads it back. Every ambiguous/error response retains that key, including component refresh/reload; a validated committed result is required before clearing it. Storage failure blocks submission and is visible. Closing the tab or clearing browser storage is outside this retention boundary. The server's durable replay survives restart within the retained database. Configuration uses optimistic version checking; its ambiguous response requires reloading/reviewing saved settings. The panel polls read-only status every 30 seconds while mounted and retains prior status with an error when refresh fails. No browser behavior has been observed.
